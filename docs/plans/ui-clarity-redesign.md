# Переработка дизайна веб-интерфейса ради понятности: проверка и план

Статус: предложение, не принято и не реализовано. Дата: 2026-10-05.
Метод: скилл `design`, поток `design-selection` (доказательства проекта →
назначение экранов и ограничения → выбор направления → запись решения →
критерии проверки). Контракт дизайна остается в корневом `DESIGN.md`; этот
документ описывает проверку и план, а раздел 8 содержит готовый текст для
`DESIGN.md`, который вносится при принятии плана.

## 1. Что проверено

- Исходники: `frontend/src/shell`, 34 Vue-компонента в `frontend/src/features`,
  `frontend/src/help`, `frontend/src/styles/styles.css` (2759 строк),
  35 RU-каталогов в `frontend/src/locales/ru`.
- Документы: `DESIGN.md` (Active, обновлен 2026-09-04), `docs/plans/expense-clarity.md`,
  `docs/plans/status-explanations.md`, `docs/plans/ui-modularization.md`,
  `docs/user/ACCOUNTING_WORKFLOW.md`, `docs/user/ACCOUNTING_STATUSES.md`,
  новый `README.md` на `origin/master` (коммит c154ca0 «Help new users understand
  the app before installation details»).
- Живой интерфейс: сборка текущего `master` (0c2e0b8) и демо-сервер на
  синтетических данных (`.claude/serve_demo.py`, конфигурация `autonomo-demo` в
  `.claude/launch.json`, порт 8765). Сняты 15 полностраничных снимков на ширине
  1440 px и 5 на ширине 375 px, локаль RU. Снимки лежат вне репозитория
  (privacy guard запрещает бинарники).
- Контраст палитры посчитан по формуле WCAG 2.2. Не проверялись: EN-локаль
  визуально, зум 200 %, режим forced-colors, реальные пользователи.
- Предыдущий раунд понятности (PR #24, 2026-08-31, влит) дал вкладки проверки,
  систему состояний и панель «Разобраться». Этот план начинается после миграции
  на Vue и не повторяет те работы.

## 2. Итог проверки

### 2.1 Что уже хорошо и сохраняется

- Страница «Налоги и сроки»: крупный заголовок состояния, одна строка
  пояснения, факты, детали расчета свернуты. Это лучшая «грамматика страницы»
  в приложении, ее и нужно распространить на остальные экраны.
- Панель «Разобраться»: причины с нумерацией, «Следующие действия», «Что
  известно», ссылка на проверку. Образец объяснения состояния.
- Вкладки проверки с счетчиками, честные пустые состояния расходов (нет
  записей / нет совпадений / на следующих страницах), стековые строки таблиц на
  мобильной ширине, спокойная зеленая палитра и системные шрифты.
- Дисциплина `null` ≠ `0`, деньги в целых минорных единицах, машинные ключи в
  API и перевод на клиенте, паритет RU/EN через `locales:check`.

### 2.2 Проблемы по убыванию влияния

1. **Нет слоя «что сделать сейчас».** Обзор состоит из желтой плашки,
   пяти карточек, зеленой плашки, шести графиков (на свежей базе три пустые:
   «Квартальные расчеты не сформированы», «Платежей к резервированию нет»),
   таблицы операций и панели вопросов. Две плашки ведут на одну и ту же
   страницу проверки одной и той же кнопкой «Открыть проверку», но на разные
   вкладки (`DashboardView.vue:121-124, 166-168, 220-229`). «Последние
   операции» видны после ~2000 px прокрутки на десктопе; на телефоне обзор
   занимает ~11 000 px.
2. **Ключевое действие спрятано.** Расчет налогов запускает только иконка «↻»
   в шапке с подсказкой «Обновить расчет» (`Shell.vue`, `controller.ts:427`).
   Карточки Modelo на обзоре показывают «— расчет не обновлен», а страница
   налогов для любого квартала без расчета говорит «Сумма пока не определена.
   Не хватает расчета или решения по обязательной декларации» красным тоном и
   без действия. Пользователь не узнает, что нужно нажать.
3. **Тупики без следующего шага.** В очереди проверки у заблокированной
   проверенной строки (валютный расход без курса) нет ни одной кнопки:
   «Открыть проверку» выводится только для `needs_review`
   (`ReviewQueue.vue`). Карточка RETA предлагает выполнить CLI-команду
   `autonomo-tax reta base add` и открыть `docs/user/RETA_CHECK.md`
   (`reta.basesHint`). «Решение по подаче не принято» и «Срок —» не говорят,
   кто и где принимает решение. Отключенная кнопка «Добавить» объясняет причину
   только в `title` (`intake.disabledReason`).
4. **Жаргон и сырые значения.** 40 RU-строк содержат латиницу вне допустимых
   терминов: «posted / included in filing», «filing snapshot», «Inbox»,
   «cleanup», «settlement-курс», «tramo», «превью», «пакет». Сырые коды:
   «G03» и «Код не определен» в колонке результата, 10 из 17 налоговых кодов
   без RU-метки (`taxCodeLabels.json`), типы документов AEAT «F1…LC»,
   подпись «invoice_review · ES» в карточке расхода, «estimacion_directa_simplificada /
   general» в настройках, ISO-метка «2026-04-03T10:20:30Z» в документах AEAT,
   ключ периода «2026-Q4» вместо «IV квартал 2026» на шести экранах, текст
   ошибок сервера по-английски (`error-message.ts:12-14`, карточки вопросов
   `GuidedReviewView.vue:704`).
5. **Четыре словаря для одних и тех же состояний.** `help.statuses.*`
   («Требуется проверка», «Готово к проведению»), `statuses.labels.*`
   («проверено», «в декларации»), `review.category.*` плюс `review.posting*`
   («можно провести», «Проверено · Можно провести сейчас»), текстовые статусы
   AEAT и графика амортизации. Карточки сводки очереди используют пятый
   набор («Нужно проверить», «Можно провести сейчас», «Блокировки после
   проверки»), карточки проведения шестой («Подтверждено», «Отложено»).
   Одно действие «открыть документ» названо четырьмя способами («Источник»,
   «Файл», «Открыть файл», «Открыть оригинал»); одно поле подписано по-разному
   на разных экранах (семь пар: «Рабочее назначение» / «Деловое назначение»,
   «Дата учета» / «Дата операции», «Документ от» / «Дата счета» / «Дата
   документа» и другие).
6. **Дубли главных действий.** На «Доходах» и «Расходах» две одинаковые
   зеленые кнопки «+ Добавить» (шапка и панель списка). В настройках два
   primary («Сохранить профиль», «Сохранить лимиты»). В форме расхода после
   «Проверить итог» одновременно видны «Проверить итог» и «Подтвердить и
   провести». Кнопка «Новый поставщик» на всю ширину выглядит как главное
   действие формы. Пять кнопок в формах без класса и со стилем браузера
   (`ExpenseWorkflowView.vue:457, 466, 469, 864, 881`, `AssetSchedule.vue:134`).
7. **Ячейка статуса перегружена.** В каждой строке каждой таблицы три строки:
   бейдж, пояснение, ссылка «Разобраться». У проведенных строк ссылка ведет в
   панель, где «следующих действий» нет и предлагается «передать бухгалтеру»
   (`help.words.noAction`). Слово «Разобраться» обещает проблему там, где ее
   нет. У непроведенных доходов пояснение «Предлагаемый вычет; еще не
   подтверждает учет в налогах» не относится к доходу.
8. **Форма проверки расхода не ведет.** 22 поля сразу (до ~40 с поставщиком,
   активом и валютой), три даты без пояснения разницы («Документ от», «Дата
   учета», «Дата записи»), поле «Причина исправления данных / отмены
   подтверждения» на первой проверке, открытые вопросы сервера не выводятся
   (`draft.source.issues` только переключает поле), после «Проверить итог»
   итог появляется ниже без прокрутки и фокуса, заметка о курсе печатается
   сырым токеном (`prior_business_day`). Слева пустая панель оригинала высотой
   в экран, когда просмотр недоступен. В guided-review три параллельных
   статуса сверху (ячейка, бейдж категории, жирный текст «Проверено · …» на
   экране, где проверка только начинается), алерт «нельзя завершить» выводится
   дважды, предупреждение «Курс не выбран» показывается при загрузке.
9. **Известное 0 и неизвестное смешаны.** На странице налогов «Подтверждено
   списано 0,00 €» рядом с «К оплате —»; в таблице заблокированных строк
   проведения «0,00 €» у валютного расхода без суммы в евро
   (`PostingRows.vue`, `normalize.ts:56`); сводка «Проверено, не проведено: —»
   и «Не хватает данных о сумме» скрывают известные 242 € из-за одной строки
   без курса.
10. **Пустые состояния не учат.** Из всех пустых текстов инструкцию дают два
    (`transactions.emptyIncome`, `settings.form.empty`). Первого запуска нет:
    поиск `onboarding|firstRun|welcome|как начать` по `frontend/src` пуст.
    Пустая очередь на пустой базе звучит как успех: «Очередь проверки пуста —
    все проверено».
11. **Иерархия заголовков.** h2 повторяет h1 на «Контрагентах» и «Документах
    AEAT»; заголовок страницы и заголовки секций на одном уровне h2 в
    guided-review, карточке расхода и налогах (пять h2); пропуск h3 в
    настройках; секции без заголовка (панель оригинала, блок IVA, панель
    графика оборудования).
12. **Мобильная ширина.** Девять пунктов навигации сеткой занимают первый
    экран (~200 px) на каждой странице; графики сжаты до нечитаемых подписей
    месяцев; пустая панель оригинала занимает ~350 px перед формой.
13. **Доступность и верстка.** Рамка полей ввода `#cbd4d0` на белом 1,51:1
    (граница компонента требует 3:1, WCAG 1.4.11); кольцо фокуса `#65bfa8`
    2,19:1; текст предупреждения `--warning #b26a12` на белом 4,23:1 (норма
    4,5:1 для обычного текста); `--accent` на белом ровно 4,50:1;
    `.primary-button:disabled` показывает курсор `wait` при блокировке по
    валидации. На 1440 px ряд фильтров AEAT выходит за панель, заголовок
    «MODELO» переносится по буквам, две кнопки в колонке действий очереди
    переносятся на две строки.

### 2.3 Корневая причина

Интерфейс рос как набор честных, точных экранов для оператора: каждая
функция получила свою панель, свой словарь и свое объяснение. Для владельца
без бухгалтерского опыта не хватает одного слоя над ними: куда смотреть
первым, что это значит и что нажать. Остальные проблемы (жаргон, дубли
кнопок, графики без данных) следствия отсутствия этого слоя и единого
контракта на словарь.

## 3. Контекст и ограничения

- **Пользователи.** Владелец: самозанятый в Испании, RU или EN, не бухгалтер,
  раз в неделю добавляет документы, раз в квартал готовит декларации, смотрит
  с ноутбука и проверяет с телефона. Оператор: технический помощник, работает
  с CLI и серверными настройками; ему нужна плотность данных и точные коды.
- **Класс экранов.** Рабочий интерфейс (очередь, проведение, списки, активы,
  контрагенты, реестр AEAT, настройки) и две поверхности принятия решений
  (обзор, налоги). Маркетинговых поверхностей нет.
- **Задачи.** Понять состояние квартала и следующий шаг; добавить документ;
  проверить и провести операцию; понять сумму к уплате и срок; убедиться, что
  ничего не забыто.
- **Платформа.** Vue 3 + TypeScript + Vite, сервер на stdlib Python со строгим
  CSP (`script-src 'self'; style-src 'self'`), без CDN, внешних шрифтов,
  иконок и инлайн-стилей. Новые зависимости не добавляются. Inter
  используется только если установлен локально, иначе системный шрифт.
- **Жесткие ограничения.** Маршруты и параметры URL сохраняются
  (`routes.ts`, e2e-тесты). Налоговая семантика, суммы и правила проведения не
  меняются. `null` ≠ `0`. Паритет RU/EN по каждому ключу. Статусы берутся
  с сервера, клиент ничего не выводит сам. Бинарники в репозиторий не попадают.
- **Доступность.** WCAG 2.2 AA: контраст текста 4,5:1, нетекстовых границ и
  индикаторов фокуса 3:1, цели указателя 24×24 CSS px, клавиатура, зум 200 %,
  forced-colors, `prefers-reduced-motion`.
- **Бренд.** Спокойная учетная книга: сохранить зеленую палитру, токены и
  компоненты; доверие через явные подписи, а не декор.

## 4. Выбор направления

Сравнивались три направления.

| Направление | Суть | Оценка |
|---|---|---|
| A. Рабочий стол задач | Обзор превращается в список задач «что сделать сейчас» (образец: компонент task list дизайн-системы GOV.UK), цифры квартала ниже, графики по порогу данных; навигация группируется; маршруты прежние | Лучше всего закрывает проблемы 1–3; стоимость средняя: переработка `DashboardView.vue`, аддитивные счетчики в `/api/dashboard` |
| B. Единая грамматика страницы | Каждому экрану шапка «что это, что не так, что сделать» и одно главное действие; один словарь состояний; технические поля свернуты; пустые состояния с инструкцией; графики только при достаточных данных | Закрывает проблемы 2, 4–11 на всех экранах; стоимость низкая и средняя: словари, разметка, один маленький компонент шапки |
| C. Пошаговый мастер | Проверка документа как «один вопрос на страницу», таблицы спрятаны за карточками | Отвергнуто |

Отвергнуто C: оператору нужны плотные таблицы и все факты рядом с
оригиналом; мастер умножает маршруты и ломает контракт URL и e2e; GOV.UK сам
допускает группировку вопросов для внутренних служб, где нужно быстро
переключаться между задачами. Выбор: **B как базовый слой на всех экранах
плюс A для обзора и навигации.** Порядок сравнения по `design-selection`:
удобство основной задачи (найти, что делать, и завершить проверку) выше
согласованности (компоненты, маршруты и токены сохраняются), выше бренда
(палитра не меняется), выше стоимости (только словари, разметка и CSS, без
новых зависимостей).

Источники, на которые опирается направление: WCAG 2.2 (контраст 1.4.3 и
1.4.11, размер цели 2.5.8 с исключениями по интервалу и инлайн-ссылкам);
GOV.UK Design System, компонент task list (строка = задача, подсказка в одну
фразу, статус тегом, вся строка кликабельна, группировка списков с
заголовками) и паттерн question pages (для внутренних служб допустимо
несколько вопросов на странице; заголовок страницы формулируется по текущему
шагу). Прочитаны 2026-10-05; паттерн task-list pages переехал в компонент
task-list, старый адрес отдает 410. `ui-ux-pro-max` не использовался:
локальных доказательств достаточно, а его генератор ориентирован на лендинги.

## 5. Принципы (войдут в DESIGN.md)

1. **Страница отвечает на три вопроса:** что это, что сейчас не так, что
   сделать. Шапка каждого экрана: заголовок, одна строка назначения, одно
   главное действие. Остальное ниже.
2. **Одно главное действие на экран.** Вторичные действия серые или
   текстовые. Два зеленых primary одновременно не допускаются (кроме модальных
   диалогов поверх страницы).
3. **Один словарь состояний.** Канонические метки записи, подачи и расчета
   (раздел 6) используются везде: бейджи, сводки, карточки, тексты плашек.
   Новые синонимы не вводятся.
4. **Техническое свернуто, объяснение рядом.** Коды AEAT, минорные единицы,
   базисные пункты, идентификаторы живут за `<details>`. Если значение
   показывается, у него есть человеческая метка; код в скобках вторичен.
5. **Неизвестно ≠ 0 ≠ не применяется,** и формулировка говорит, чего не
   хватает и как получить: «Расчет не выполнен. Рассчитать», «242,00 € и одна
   операция без суммы в EUR», а не «—».
6. **Нет тупиков.** Любой блокирующий статус показывает действие или
   владельца действия («записывает оператор по резолюции TGSS»). CLI-команды и
   пути к файлам репозитория в интерфейсе владельца не появляются.
7. **Пустое состояние учит.** Говорит, почему пусто, и предлагает следующий
   шаг с кнопкой. Пустая база отличается от «все сделано».
8. **Графики после действий и по порогу данных.** График рисуется, когда в
   наборе не меньше двух ненулевых точек; иначе одна строка текста. На телефоне
   таблица данных первична, график раскрывается.
9. **Плотность для оператора не теряется.** Таблицы, коды и факты остаются
   доступными на том же экране, но ниже или за разворачиванием.

## 6. Канонический словарь

Один набор меток на все экраны (RU, EN добавляется зеркально). Порядок
соответствует жизненному циклу; метки готовности сочетаются с «Проверено».

| Состояние (код) | Было (разные экраны) | Станет RU | Станет EN |
|---|---|---|---|
| `received` | Документ получен / получено | Документ получен | Document received |
| `extracted` | Данные извлечены / извлечено | Данные извлечены, ждет проверки | Extracted, awaiting review |
| `needs_review` | Требуется проверка / нужна проверка / Нужно проверить решение по счету | Требуется проверка | Review required |

## 7. План работ

Каждый этап отдельный draft PR в `master`, без выкладки на прод, без
изменений налоговой семантики и схемы. Этапы 0–2 дешевые и дают наибольший
эффект на всех экранах; 3–5 переделывают три ключевых экрана; 6–7 закрывают
пустые состояния, мобильную ширину и доступность; 8 по решению владельца.
Размеры: S до ~200 строк диффа, M до ~600, L больше.

### Этап 4. Проверка: очередь и проведение (M)

- В каждой строке очереди действие по состоянию: `needs_review` → «Открыть
  проверку»; `approved + blocked` → «Что мешает» (панель причин с действиями;

  ready` → «Провести» (переход на вкладку проведения с подсветкой строки);

- Карточки сводки очереди становятся фильтрами таблицы (кнопки с

  отложенные и заблокированные; статистика «Перенос оригиналов в архив»

  таблиц уменьшается примерно вдвое.
- График «Очередь разбора по срокам» показывается только при ≥ 10 операциях в
  очереди, иначе одна строка «Самая старая операция в очереди: N дней».

## Clarity redesign (round 2)

- Status: Draft, proposed 2026-10-05 in docs/plans/ui-clarity-redesign.md.

  purpose, one primary action, technical detail collapsed) plus a task list
  on the dashboard. Rejected: a one-question-per-page wizard (breaks the
  URL/test contract and removes the facts-beside-source layout operators
  need); keeping the analytics-first dashboard (does not answer "what now").
- References: WCAG 2.2 SC 1.4.3, 1.4.11, 2.5.8; GOV.UK Design System task
  list component (whole-row links, one-sentence hints, status tags, grouped
  lists) and question pages pattern (grouped questions are acceptable for
  internal services; headings name the current step). Transferable: hierarchy
  and status feedback. Not transferable: GOV.UK typography, colours and the
  one-question flow.

  dialogs; RU catalogs contain no Latin service words outside the allowed
  term list; every blocking status shows an action or its owner; every empty
  state names the next step; charts render only with at least two non-zero
  points; dashboard first screen at 375 px shows tasks, not charts.

### Page grammar
- Header: h1 title, one-line purpose, one primary action. Sections start at
  h2, nested at h3; no heading repeats the title; no section without a heading.
- One primary button per screen; secondary and text buttons for the rest.
  Disabled controls explain why in visible text, never only in `title`.
- Technical values (AEAT codes, minor units, basis points, identifiers) live
  behind `<details>`; a shown code always follows its human label.

### Status vocabulary
- One catalog (`statuses.*`) supplies every lifecycle, readiness, filing and
  calculation label; see the canonical table in the plan. Synonym keys are
  removed. A status cell is a badge plus at most one line of reason; the
  details link appears only when a reason or an action exists.
- Unknown, zero and not applicable are worded, not dashed, whenever the
  missing piece has a known cause: "Not calculated yet. Calculate",
  "242.00 € plus 1 operation without a EUR amount".

### Empty states and first run
- Each empty state says what is empty, why, and offers the next step with a
  control. An empty ledger shows a four-step start list on the dashboard
  until the first posting; an empty review queue distinguishes "no documents
  in this quarter" from "everything reviewed".

### Charts
- A chart renders only when its dataset has at least two non-zero buckets;
  otherwise the slot shows one line of text. Dashboard charts sit below the
  task list and quarter figures; on narrow screens the data table is primary
  and the chart is collapsed. The queue aging chart renders from ten queued
  items.

### Accessibility tokens
- Control borders at least 3:1 against the surface; focus ring
  `--accent-dark` 2 px; warning text token at least 4.5:1; disabled primary
  buttons use `cursor: not-allowed`; pointer targets at least 24×24 CSS px
